# Course Reflection

The most challenging concept in this course was mastering database concurrency control and distributed race conditions—specifically navigating transaction isolation levels, row-level locking, and deadlocks under flash-traffic spikes. Initially, it was difficult to visualize how simultaneous database writes collide and exhaust connection pools. I overcame this by drawing step-by-step transaction timeline diagrams, simulating race conditions in local PostgreSQL instances using concurrent client threads, and implementing optimistic locking with version columns and in-memory Redis atomic scripts to absorb contention before it hits disk.

Based on the feedback I received on my capstone project, I would significantly improve the data caching and cache-invalidation architecture. In my initial implementation, the cache invalidation strategy relied on blunt time-to-live (TTL) expiration, which created brief windows of stale data during rapid inventory updates. To address this, I would adopt event-driven cache invalidation using Redis Pub/Sub and Change Data Capture (CDC) with Debezium, alongside strict database unique constraints to guarantee zero inconsistencies between the cache and persistent storage.

Moving forward, I will dive deeper into distributed systems engineering. My next learning focus centers on event-driven streaming architectures using Apache Kafka, exploring the Raft consensus algorithm, and mastering container orchestration with Kubernetes. Understanding how distributed message brokers handle partitioned event ordering, idempotency, and backpressure under massive scale will enable me to build even more resilient, fault-tolerant web platforms.
